Migration guide (v2 → v3) v2 withdrawn

v2 of the Events endpoint was withdrawn on 2026-08-21. This guide covers the changes you need to handle to move your integration to v3. Most changes are backward-compatible — expect a smooth upgrade.

v2 is no longer supported

v2 endpoints no longer accept requests. If you're seeing 404s on /v2/* paths for the Events endpoint, that's why — there is no grace-period fallback.

See v3 Events endpoint for the new API.

1. Update base URL and paths

Change from /v2/ to /v3/ in your API calls.

{{ds:component/code-block|filename=diff|language=diff|code=- GET /v2/pipelines/{pipeline_id}/events + GET /v3/pipelines/{pipeline_id}/events - POST /v2/events/{id}/replay + POST /v3/events/{id}/replay}}

2. New filtering parameters

v3 adds optional until (upper bound timestamp) and status filters. These are backward-compatible — if you're not using them, your v2 code works as-is.

Name Type Required Description
untilstringNo(New in v3) ISO-8601 upper bound on occurred_at.
statusstringNo(New in v3) Filter by pending, delivered, failed, or dead-lettered.
example-v3-filter.sh bash 
# New: filter events by status to find dead-lettered ones
curl -X GET 'https://api.godzilladocs.dev/v3/pipelines/pipe_123/events?status=dead-lettered' \\\\
  -H "Authorization: Bearer $GODZILLA_API_KEY"

3. Batch replay (optional)

v3 introduces a new replay-batch endpoint for replaying multiple dead-lettered events in a single request. v2 required individual replay calls per event.

batch-replay.sh bash 
# Replay all dead-lettered events from a specific time range
curl -X POST 'https://api.godzilladocs.dev/v3/pipelines/pipe_123/events/replay-batch' \\\\
  -H "Authorization: Bearer $GODZILLA_API_KEY" \\\\
  -H "Content-Type: application/json" \\\\
  -d '{
    "since": "2026-08-20T00:00:00Z",
    "until": "2026-08-21T00:00:00Z"
  }'

Response shape changes

Event objects now include a status field (v3 only):

event-v3.json json 
{
  "id": "evt_8f2c1a90",
  "type": "order.created",
  "occurred_at": "2026-08-18T09:12:44Z",
  "status": "delivered",
  "payload": { "order_id": "ord_4471" }
}

The status field is one of:

  • pending — event is being processed
  • delivered — successfully sent to destination
  • failed — delivery failed but will be retried
  • dead-lettered — delivery failed after all retries exhausted

Coming from v1?

If you're migrating from v1, you'll need to handle cursor pagination and the error shape changes. See the v1 → v2 migration guide for those details, then follow the steps above for v2 → v3.
