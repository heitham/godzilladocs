Migration guide (v2 → v3) Recommended

v3 ships with event retention configuration — a simple but powerful feature for compliance-driven pipelines. The migration is minimal: the endpoint remains backward-compatible, so you can upgrade at your own pace.

What's new in v3

v3 adds a single new optional parameter to pipeline creation and updates:

  • retention_days — Control how long events are kept in each pipeline (1–365 days, default: 30). Allows fine-grained control over data lifecycle and compliance obligations without blanket org-wide policies.

All other endpoints and parameters remain unchanged.

Update client code

When you upgrade to v3, change your base URL and optionally add retention_days to any pipeline creation requests:

diff diff 
- POST https://api.godzilladocs.dev/v2/pipelines
+ POST https://api.godzilladocs.dev/v3/pipelines

  {
    "name": "ingest-orders",
    "source_connector_id": "conn_pg_orders",
    "destination_connector_id": "conn_snowflake_dw",
+   "retention_days": 90
  }

New compliance features

Per-pipeline retention policies let you handle mixed data classifications in a single workspace:

  • PII pipelines — Set retention_days: 7 to comply with short data minimization windows.
  • Analytics pipelines — Set retention_days: 365 for longer historical context.
  • Audit logs — Set retention_days: 30 to meet standard compliance standards.

v3 enforces retention at the pipeline level, so different data flows can have independent lifespans.

Migration timeline

v2 will continue to work until end-of-life. No breaking changes are planned in 2026. Start with v3 on new integrations; migrate existing ones at your convenience.

v3 is backward-compatible

Omitting retention_days defaults to 30 days, matching v2 behavior. You can upgrade your base URL immediately and add retention policies gradually.

Migration notes

  • Events created under v2 inherit the new retention period retroactively — existing pipelines updated to v3 will apply the new retention_days to all retained events.
  • SDK clients may cache the v2 base URL — clear any cached configuration and redeploy.
  • The retention_days limit is enforced at request time; validation happens server-side, so older SDKs will still send valid requests to v3.
