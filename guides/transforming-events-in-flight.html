Transforming events in flight

As events flow from a source connector to a destination connector, you can modify them in real time. This guide covers how to reshape payloads, filter out unwanted records, and enrich events with additional context inside a pipeline.

Configuring transforms

Transforms are defined as an ordered list in the transforms array of your pipeline definition. When creating or updating a pipeline via the Pipelines endpoint, specify one or more transform steps.

pipeline-transforms.json json 
{
  "name": "orders-etl",
  "source_connector_id": "conn_pg_orders",
  "destination_connector_id": "conn_snowflake_dw",
  "transforms": [
    {
      "type": "filter",
      "condition": "payload.status == 'completed'"
    },
    {
      "type": "reshape",
      "mapping": {
        "order_id": "payload.id",
        "total_amount": "payload.amount_cents / 100",
        "customer_email": "payload.email"
      }
    },
    {
      "type": "enrich",
      "fields": {
        "processed_at": "$now",
        "environment": "production"
      }
    }
  ]
}

Reshaping payloads

Use reshape transforms to map incoming fields to target schema structures, rename keys, calculate derived values, or drop unnecessary nested data before writing to the destination.

OperationExample mapping
Field renaming{ "user_id": "payload.account_id" }
Calculations{ "amount_usd": "payload.amount_cents / 100" }
Flattening nested fields{ "city": "payload.address.city" }

Filtering events

Filter steps evaluate a boolean condition against each event. Events that evaluate to true proceed to the next step, while events evaluating to false are dropped cleanly without triggering an error or alerting the dead-letter queue.

Filter early for performance

Place filter steps at the beginning of the transforms list to avoid executing unnecessary reshape or enrichment steps on records that will ultimately be discarded.

Enriching events

Enrichment steps append new metadata or computed context to the event payload. Common enrichments include injecting processing timestamps ($now), platform metadata, or static environment tags needed by downstream analytics systems.

Error handling in transforms

If an event encounters an unhandled evaluation error during a transform step (such as a type mismatch or missing required field), it is retried according to the pipeline's retry policy before being sent to the dead-letter queue. See Handling errors & retries for details on debugging and replaying failed transforms.
