Transforming events in flight

Once you've connected a source and a destination, the next step is to shape and enrich your data. This guide covers how to use transforms to reshape fields, filter events, and enrich your data as it flows through your pipeline.

What are transforms?

A transform is a function that runs on every event as it passes through your pipeline, after it's read from the source but before it reaches the destination. Transforms can:

  • Reshape fields (rename, extract, flatten, or nest data)
  • Filter events (drop events that don't meet criteria)
  • Enrich events (add new fields, lookup data, compute derived values)
  • Validate events (ensure required fields and data types)

Adding a transform to your pipeline

Transforms are added as a stage between your source and destination connectors. When you create or edit a pipeline, you can insert one or more transforms into the event flow.

pipeline-with-transform.json json 
{\n  \"name\": \"customer-sync\",\n  \"source\": {\n    \"connector_id\": \"postgres-prod\",\n    \"table\": \"customers\"\n  },\n  \"transforms\": [\n    {\n      \"type\": \"reshape\",\n      \"mappings\": {\n        \"customer_id\": \"id\",\n        \"email_address\": \"email\"\n      }\n    }\n  ],\n  \"destination\": {\n    \"connector_id\": \"webhook-crm\"\n  }\n}

Reshaping fields

Reshape transforms let you rename, extract, or reorganize fields in your event. This is useful when your source and destination use different field names or structures.

reshape-example.json json 
{\n  \"type\": \"reshape\",\n  \"mappings\": {\n    \"customer_id\": \"id\",\n    \"order_amount\": \"total_price\",\n    \"created_at\": \"timestamp\"\n  }\n}

For nested data, use dot notation to extract or create nested fields:

nested-reshape.json json 
{\n  \"type\": \"reshape\",\n  \"mappings\": {\n    \"user.first_name\": \"first_name\",\n    \"user.last_name\": \"last_name\",\n    \"billing_address.zip\": \"zip_code\"\n  }\n}

Filtering events

Filter transforms drop events that don't match a condition, so only relevant data reaches your destination.

Filtered events are not retried

When an event is filtered out, it's considered successfully processed and won't appear in your dead-letter queue.

filter-example.json json 
{\n  \"type\": \"filter\",\n  \"condition\": \"event.order_amount > 100\"\n}

Enriching events

Enrichment transforms add new fields to your events, pulling data from external sources, computing derived values, or adding context.

enrichment-example.json json 
{\n  \"type\": \"enrich\",\n  \"lookups\": [\n    {\n      \"field\": \"user_id\",\n      \"source\": \"user-database\",\n      \"target_field\": \"user_profile\"\n    }\n  ],\n  \"computed_fields\": {\n    \"total_vat\": \"event.order_amount * 0.2\",\n    \"region\": \"event.country.substring(0, 2)\"\n  }\n}

Chaining transforms

Multiple transforms execute in order: the output of one becomes the input to the next. This lets you build complex logic step by step.

chained-transforms.json json 
{\n  \"transforms\": [\n    { \"type\": \"filter\", \"condition\": \"event.status !== 'cancelled'\" },\n    { \"type\": \"reshape\", \"mappings\": { \"order_id\": \"id\" } },\n    { \"type\": \"enrich\", \"computed_fields\": { \"processed_at\": \"new Date().toISOString()\" } }\n  ]\n}

Testing transforms

Before deploying a transform to production, use the pipeline preview feature to run a sample event through your transforms and see the output. This helps catch logic errors early.

Performance considerations

Each transform adds latency to your event processing. For high-throughput pipelines, consider:

  • Combining multiple field mappings into a single reshape transform
  • Placing filter transforms early to reduce data moving through subsequent transforms
  • Using batch enrichment lookups when possible instead of per-event lookups
