Transforming events in flight

This guide covers reshaping, filtering, and enriching events as they flow through your pipeline using transforms — a powerful way to clean, unify, and augment data without leaving your pipeline.

What are transforms?

A transform is a processing step in a pipeline that takes each event and can:

  • Reshape — change field names, flatten nested objects, or reorganize the structure
  • Filter — drop events that don't match a condition
  • Enrich — add computed fields, lookups, or derived values

Transforms run synchronously as events flow through the pipeline, before they reach the destination.

Common transform patterns

Field mapping and restructuring

Map source field names to a canonical schema:

transform-example.json json 
{\n  "user_id": "userId",\n  "full_name": "fullName",\n  "email_addr": "email"\n
}

Filtering events

Use a condition to exclude events that don't meet criteria:

filter-example.json json 
{\n  "condition": "event.status == 'active'",\n  "action": "keep"\n
}
Filter behavior

When an event fails a filter condition, it is silently dropped. Events are not sent to the dead-letter queue unless there's an error in the transform logic itself.

Enrichment with computed fields

Add new fields derived from existing data:

{{ds:component/code-block|filename=enrich-example.json|language=json|code={\n "new_fields": {\n "event_year": "year(event.timestamp)",\n "is_vip": "event.lifetime_value > 10000",\n "region": "lookup_region(event.postal_code)"\n }\n}}}

Transform limitations

Keep these constraints in mind when designing transforms:

  • Transforms must complete within 5 seconds per event
  • No external API calls or network I/O — use enrichment data pre-loaded into the transform
  • Memory is limited to 256MB per transform instance
  • Transforms are stateless — no persistent caches across events

Error handling in transforms

If a transform fails on an event:

  1. The pipeline logs the error with the event and transform details
  2. The event is sent to the dead-letter queue
  3. The pipeline continues processing subsequent events
Transform errors are retryable

Events in the dead-letter queue from transform failures can be replayed after you fix the transform logic. See Handling errors & retries for replay instructions.

Performance considerations

Transforms are synchronous and run on the critical path, so keep them fast:

  • Use simple field mappings instead of complex logic when possible
  • Cache lookup tables or reference data inside the transform at startup
  • Test transforms with realistic event volume before deploying to production

Next steps
