Transforming events in flight

\n

Once you've connected a data source, events flow through your pipeline as structured data. This guide covers how to reshape, filter, and enrich those events before they reach their destination.

\n\n

Overview

\n

Transformations apply at the pipeline level and run on every event that enters the pipeline. You can:

\n
    \n
  • Reshape — flatten nested objects, rename fields, or project a subset of columns
    • \n
  • Filter — discard events matching certain criteria (e.g., test events, low-value rows)
    • \n
  • Enrich — add new fields by joining external data or deriving values from existing fields
    • \n
\n\n

Reshaping events

\n

The most common transformation is projecting fields — keeping only the columns you need and renaming them for the destination system.

\n\n
\n
\n transform-project.json\n json\n \n
\n 
{\n  \"transform\": {\n    \"type\": \"project\",\n    \"fields\": {\n      \"user_id\": \"id\",\n      \"user_email\": \"email\",\n      \"user_created_at\": \"created_at\"\n    }\n  }\n}
\n
\n\n

This transformation reads the id, email, and created_at fields from incoming events and emits them as user_id, user_email, and user_created_at. Any other fields are dropped.

\n\n
\n
Flattening nested objects
\n

Use dot notation in field names to flatten nested objects: \"address.city\" becomes a top-level city field, or map it to any name you prefer.

\n
\n\n

Filtering events

\n

Filter transforms discard events matching a predicate, reducing noise and cost by not storing or processing unwanted data.

\n\n
\n
\n transform-filter.json\n json\n \n
\n 
{\n  \"transform\": {\n    \"type\": \"filter\",\n    \"condition\": {\n      \"field\": \"status\",\n      \"operator\": \"!=\",\n      \"value\": \"test\"\n    }\n  }\n}
\n
\n\n

This filter drops all events where the status field is test. Only events with a non-test status are passed to the destination. Filtered events do not incur downstream costs and do not appear in the dead-letter queue.

\n\n

Enriching events

\n

Enrichment adds new fields to events by consulting an external source — a dimension table, a cache, or a derived calculation.

\n\n
\n
\n transform-enrich.json\n json\n \n
\n 
{\n  \"transform\": {\n    \"type\": \"enrich\",\n    \"lookups\": {\n      \"customer_tier\": {\n        \"source\": \"dimension_customers\",\n        \"match_on\": \"customer_id\",\n        \"select\": \"tier\"\n      }\n    }\n  }\n}
\n
\n\n

This enrichment joins the incoming customer_id against a dimension table called dimension_customers, looks up the tier column, and adds it as a new field on every event.

\n\n
\n
Enrichment latency
\n

External lookups add latency to each event. Keep dimension tables small and indexed on the join key. For high-volume pipelines, consider caching or materializing the lookup data closer to the pipeline.

\n
\n\n

Combining transformations

\n

You can chain multiple transforms in a single pipeline — they run left to right. A common pattern is filter first (drop unwanted rows early), then project, then enrich.

\n\n
\n
\n pipeline-multi-transform.json\n json\n \n
\n 
{\n  \"pipeline_id\": \"enrich-and-filter-orders\",\n  \"transforms\": [\n    { \"type\": \"filter\", \"condition\": { \"field\": \"amount\", \"operator\": \">\", \"value\": 0 } },\n    { \"type\": \"project\", \"fields\": { \"order_id\": \"id\", \"order_amount\": \"amount\", \"customer_id\": \"cust_id\" } },\n    { \"type\": \"enrich\", \"lookups\": { \"customer_tier\": { \"source\": \"dimension_customers\", \"match_on\": \"customer_id\", \"select\": \"tier\" } } }\n  ]\n}
\n
\n\n

Performance and debugging

\n

Check the pipeline's transform metrics in the monitoring dashboard (see Monitoring & alerts) to watch transform latency and filter drop rates. If transforms are too slow or your enrichment lookups time out, you'll see pipeline events queue up — review and optimize the transform definition.
