Transforming events in flight

On this page
  • Reshaping events
  • Filtering events
  • Enriching events
  • Chaining transforms
  • Monitoring transformations

Once events enter a pipeline, you can reshape their structure, filter out unwanted records, and enrich them with data from external sources — all before they reach the destination. This guide covers the three main transformation patterns.

Reshaping events

A reshape transformation maps fields from the source schema into a new output schema. This is useful when your destination expects a different structure than your source provides, or when you want to rename or reorganize fields.

{{ds:component/code-block|filename=reshape-transform.json|language=json|code={\n \"type\": \"reshape\",\n \"input_schema\": {\n \"customer_id\": \"string\",\n \"order_amount\": \"number\",\n \"timestamp\": \"string\"\n },\n \"mappings\": {\n \"customer_id\": \"customerId\",\n \"order_amount\": \"totalPrice\",\n \"timestamp\": \"createdAt\"\n }\n}}}

You can also project only a subset of fields, drop sensitive data before it reaches the destination, or flatten nested structures.

Type coercion
Reshape transformations can perform basic type conversion: string to number, epoch milliseconds to ISO timestamp, and boolean from string "true"/"false".

Filtering events

A filter transformation passes events through a condition and drops any that don't match. This prevents your destination from filling up with irrelevant records.

{{ds:component/code-block|filename=filter-transform.json|language=json|code={\n \"type\": \"filter\",\n \"condition\": {\n \"field\": \"order_amount\",\n \"operator\": \"gte\",\n \"value\": 100\n }\n}}}

Filters support comparison operators (eq, neq, gt, gte, lt, lte), string operations (contains, starts_with, ends_with), and logical combinations using and, or, and not.

Filtered events are dropped
An event that fails a filter is silently discarded — it doesn't retry, doesn't go to the dead-letter queue, and is not sent to the destination. Use filters when you're confident you want to discard non-matching records.

Enriching events

An enrichment transformation fetches additional data from an external source (a database, API, or reference table) and adds it to the event payload. This is useful for adding context that the source system doesn't provide.

{{ds:component/code-block|filename=enrich-transform.json|language=json|code={\n \"type\": \"enrich\",\n \"source\": {\n \"type\": \"http\",\n \"url\": \"https://api.example.com/customers/{customer_id}\",\n \"auth\": \"bearer\"\n },\n \"output_field\": \"customer_details\"\n}}}

Enrichments extract fields from the event (like a customer ID) to look up external data, then add the response to the event before sending it downstream. If an enrichment request fails or times out, the event retries with the standard backoff policy — see Error handling & recovery for details.

Enrichment adds latency
Every enrichment HTTP call adds network round-trip time to event processing. For high-volume pipelines, keep enrichment APIs fast or batch-request multiple records at once.

Chaining transforms

You can apply multiple transforms to a single pipeline in sequence: reshape first to normalize fields, then enrich to add context, then filter to drop unwanted records before they reach the destination.

Transforms execute in the order you define them, and any error in a transform (including enrichment failures) triggers the standard retry logic. A successful transform passes its output to the next transform in the chain.

Monitoring transformations

Track the success rate and latency of each transform in your pipeline's monitoring dashboard. Filter drops are counted separately from errors so you can distinguish between discarded events (which are intentional) and actual failures (which may need attention).
