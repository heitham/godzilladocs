Transforming events in flight

This guide covers how to reshape, filter, and enrich events as they flow through a pipeline.

Overview

Transforms let you modify events between the source and destination. You can extract fields, rename properties, filter out unwanted events, and enrich data with context from external sources — all without leaving the pipeline.

Reshaping events

Use a map transform to extract, rename, or restructure fields. Map expressions use a JSON-like syntax to build new event shapes:

{{ds:component/code-block|filename=map-transform.json|language=json|code={ "type": "map", "expression": { "id": ".user_id", "email": ".contact.email", "signup_date": ".created_at", "tier": ".account_type" } }}}

The map above extracts user_id, pulls email from a nested path, and renames created_at to signup_date. Fields not referenced are dropped.

Paths use dot notation

Paths starting with a dot (e.g., .user_id) refer to event fields. Literal strings and objects are passed through unchanged.

Filtering events

A filter transform stops an event from flowing further down the pipeline if a condition is false:

filter-transform.json json 
{
  "type": "filter",
  "condition": ".event_type == 'purchase'"
}

Only events where event_type is purchase continue downstream. Others are silently dropped (not dead-lettered).

Filtered events don't error

Filtering an event is a normal discard — it does not trigger retries or dead-lettering. Use filters to trim events that are valid but not relevant to this pipeline.

Enriching events

An enrich transform calls an external API or lookups table to add context to an event. Use enrichment to join in reference data without a separate JOIN step:

enrich-transform.json json 
{
  "type": "enrich",
  "lookup": "pricing_table",
  "key": ".product_id",
  "fields": ["price", "currency", "discount"]
}

For each incoming event, the enrich step looks up the product in pricing_table using product_id and merges price, currency, and discount into the event.

Chaining transforms

Combine multiple transforms in sequence. Each transform sees the output of the previous one:

{{ds:component/code-block|filename=pipeline-transforms.json|language=json|code={ "transforms": [ { "type": "filter", "condition": ".event_type == 'order'" }, { "type": "enrich", "lookup": "customers", "key": ".customer_id", "fields": ["tier", "region"] }, { "type": "map", "expression": { "id": ".order_id", "customer": ".customer_id", "tier": ".tier", "total": ".amount" } } ] }}}

This pipeline filters to orders, joins in customer tier and region, and shapes the output.

Performance considerations

Transforms run synchronously on every event, so optimize for latency:

  • Map is fast — it reshapes in-memory.
  • Filter is fast — it evaluates a simple condition per event.
  • Enrich can be slow — it makes an external call or lookup per event. Use caching and batch enrichment where possible.

If an enrich transform times out or errors, the event retries according to your pipeline retry policy.

Common patterns

De-duplicate on ingest

Use a filter to drop events with a dedupe_id already seen in the last N hours:

dedup-filter.json json 
{
  "type": "filter",
  "condition": ".dedupe_id NOT IN cache('recent_ids')"
}

Route to different destinations

Set a routing key during transform, then split the pipeline:

{{ds:component/code-block|filename=routing-map.json|language=json|code={ "type": "map", "expression": { "user_id": ".user_id", "event": ".event_type", "route": ".event_type == 'purchase' ? 'sales_channel' : 'analytics_channel'" } }}}

Next steps

Transform rules are defined per-pipeline. See your pipeline's configuration documentation or reach out to support to set up transforms for your use case.
