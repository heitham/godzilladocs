Schemas

A schema defines the structure, types, and constraints of the data in an event's payload. It acts as a contract between your source and destination systems, ensuring data integrity as it flows through a pipeline.

Why schemas matter

Schemas serve three critical functions:

  • Validation — Incoming events are checked against the schema before processing. Invalid events fail fast rather than corrupt your destination data.
  • Type safety — Explicit field types (string, number, boolean, timestamp, etc.) let connectors handle serialization and conversion correctly.
  • Documentation — The schema is a living record of what data your pipeline expects, visible to anyone building transforms or debugging issues.

Schema declaration

Schemas are declared in JSON Schema format and attached to a pipeline at configuration time. Every source connector has a schema field that describes the shape of events it will emit.

pipeline.config.json json 
{\n  \"name\": \"ingest_orders\",\n  \"source\": {\n    \"connector_type\": \"postgres\",\n    \"connection_id\": \"conn_prod_pg\",\n    \"schema\": {\n      \"type\": \"object\",\n      \"properties\": {\n        \"order_id\": { \"type\": \"string\" },\n        \"customer_id\": { \"type\": \"string\" },\n        \"amount_cents\": { \"type\": \"integer\" },\n        \"created_at\": { \"type\": \"string\", \"format\": \"date-time\" },\n        \"status\": { \"type\": \"string\", \"enum\": [\"pending\", \"completed\", \"failed\"] }\n      },\n      \"required\": [\"order_id\", \"customer_id\", \"amount_cents\"]\n    }\n  }\n}

In this example, the pipeline expects events with order_id, customer_id, and amount_cents as required fields, with status restricted to a fixed set of values.

Validation and error handling

When an event arrives that does not match the schema:

  • If a required field is missing, the event fails validation and enters the dead-letter queue.
  • If a field has the wrong type (e.g., a string where an integer is expected), the pipeline attempts coercion. If coercion fails, the event is dead-lettered.
  • If a field value violates a constraint (e.g., an enum value not in the allowed list), the event fails validation.
Dead-letter queues

Failed validation does not retry. Invalid events go straight to your pipeline's dead-letter queue for manual inspection and replay. See Handling errors & retries for how to drain and replay them.

Schema evolution

As your data sources change, you will need to evolve your schema. Godzilla allows you to:

  • Add optional fields — New fields with required: false do not break existing events.
  • Expand enum values — Add new allowed values to a constrained field without breaking old data.
  • Loosen type constraints — Relax a field from a specific type to a union type (though this requires a pipeline version bump).

Breaking changes — removing required fields, narrowing types, or shrinking enum values — require a new pipeline version and may require replay of older events under the new schema.

Common field types

common-types.json json 
{\n  \"string\": { \"type\": \"string\" },\n  \"email\": { \"type\": \"string\", \"format\": \"email\" },\n  \"timestamp\": { \"type\": \"string\", \"format\": \"date-time\" },\n  \"integer\": { \"type\": \"integer\" },\n  \"decimal\": { \"type\": \"number\" },\n  \"boolean\": { \"type\": \"boolean\" },\n  \"array\": { \"type\": \"array\", \"items\": { \"type\": \"string\" } },\n  \"object\": { \"type\": \"object\", \"properties\": { \"key\": { \"type\": \"string\" } } },\n  \"enum\": { \"type\": \"string\", \"enum\": [\"active\", \"inactive\"] }\n}

For timestamps, always use format: "date-time" to ensure consistent parsing across connectors and transforms.

Relationship to Events

Every event flowing through a pipeline carries a payload field that must conform to the pipeline's schema. The schema is the definition; the payload is the instance. Understanding both concepts together is essential for building reliable pipelines.
