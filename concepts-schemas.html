Schemas

A schema is a formal definition of the shape and type of an event's payload. Schemas declare which fields are present, what data types they hold, whether they are required or optional, and any validation constraints. Godzilla uses schemas to validate events at ingestion, document your data contract, and catch errors before they propagate downstream.

Why schemas matter

Without schemas, your pipelines are fragile: a source connector might emit an unexpected field, a transform might assume a field is a string when it's actually a number, or a destination might reject events because required fields are missing. Schemas make these contracts explicit and checkable.

  • Validation — Events are checked against the schema at every step (ingestion, after transform, before destination write). Invalid events are rejected or moved to the dead-letter queue.
  • Documentation — Your team knows exactly what shape to expect from a source or pipeline stage.
  • Evolution — Schemas version alongside your data, so you can deprecate fields, add required ones, and evolve your contract safely.
  • Debugging — Schema validation errors include the exact field and reason, making it fast to fix broken pipelines.

Schema format

Godzilla uses a JSON Schema–like format to define event payloads. Each schema specifies:

pipeline-schema.json json 
{\n  \"$schema\": \"http://json-schema.org/draft-07/schema#\",\n  \"type\": \"object\",\n  \"properties\": {\n    \"order_id\": { \"type\": \"string\" },\n    \"customer_id\": { \"type\": \"string\" },\n    \"total_cents\": { \"type\": \"integer\", \"minimum\": 0 },\n    \"items\": {\n      \"type\": \"array\",\n      \"items\": {\n        \"type\": \"object\",\n        \"properties\": {\n          \"sku\": { \"type\": \"string\" },\n          \"qty\": { \"type\": \"integer\" }\n        },\n        \"required\": [\"sku\", \"qty\"]\n      }\n    },\n    \"shipped_at\": { \"type\": \"string\", \"format\": \"date-time\" }\n  },\n  \"required\": [\"order_id\", \"customer_id\", \"total_cents\"]\n}

Schema properties define the payload structure:

  • type — The JSON type: string, integer, number, boolean, array, object, or null.
  • required — An array of field names that must be present; missing required fields cause validation to fail.
  • properties — For objects, the nested schema for each field.
  • minimum / maximum — Numeric bounds.
  • pattern — A regex the string must match (e.g., for email or UUID validation).
  • format — Built-in formats like date, date-time, email, uri.

Attaching schemas to pipelines

When you create a pipeline, you attach a schema to the source connector's output. Godzilla then validates every event from that source against that schema. If the source is a database table, the schema is often inferred from the table structure; if the source is an HTTP webhook or Kafka topic, you define the schema by hand.

Schema inference

Many built-in source connectors (Postgres, MySQL, Snowflake) can auto-infer the schema from the source system itself — for example, reading column names and types from a table definition. This inference becomes the default schema, which you can override or refine.

Validation during transforms

After a transform step, events are re-validated against the original schema (or a new schema, if you've declared one for the transform's output). This catches bugs early: if your transform accidentally drops a required field or changes a field's type, validation fails immediately, and the event is logged and dead-lettered rather than silently propagating bad data downstream.

Schema evolution

Schemas can be versioned. When you update a pipeline's schema (e.g., adding a new optional field, or making an optional field required), you can do so with a grace period or migration window so that upstream systems have time to adapt. The Godzilla API lets you query which schema version is active for a pipeline and view the history of schema changes.
