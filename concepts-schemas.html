Schemas

A schema declares the expected shape and type constraints for the payload field of an event. Schemas enable validation, type safety, and documentation across your data pipelines.

Why schemas matter

Event payloads can vary widely depending on their source. A schema serves three purposes:

  • Validation — Godzilla rejects or dead-letters events that do not match the schema, preventing bad data from flowing downstream.
  • Type safety — Transforms and destination connectors know exactly which fields exist, their types, and whether they are nullable.
  • Documentation — Your team and integrators understand the contract every event must fulfill.

Schema declaration

Schemas are defined at the connector level and inherited by any pipeline that uses that connector as a source. They are expressed in JSON Schema format, a standardized way to describe JSON structure.

{{ds:component/code-block|filename=schema-example.json|language=json|code={\n \"$schema\": \"http://json-schema.org/draft-07/schema#\",\n \"type\": \"object\",\n \"required\": [\"order_id\", \"amount_cents\"],\n \"properties\": {\n \"order_id\": {\n \"type\": \"string\",\n \"pattern\": \"^ord_[a-z0-9]{6,}$\",\n \"description\": \"Unique order identifier\"\n },\n \"amount_cents\": {\n \"type\": \"integer\",\n \"minimum\": 0,\n \"description\": \"Order total in cents (USD)\"\n },\n \"customer_id\": {\n \"type\": [\"string\", \"null\"],\n \"description\": \"Optional reference to a customer record\"\n },\n \"tags\": {\n \"type\": \"array\",\n \"items\": { \"type\": \"string\" },\n \"description\": \"Arbitrary labels applied to this order\"\n }\n }\n}}}\n\n

Validation behavior

\n

When an event arrives at a pipeline:

\n
    \n
  1. Its payload is extracted and validated against the source connector's schema.
    2. \n
  2. If validation succeeds, the event proceeds to any transform steps.
    3. \n
  3. If validation fails, the event is either rejected (with a configurable action) or placed in the pipeline's dead-letter queue.
    4. \n
\n\n
Schema Evolution

Schemas can change over time. Use required and additionalProperties carefully: making a field required breaks older data; setting additionalProperties: false rejects new fields from upgraded sources.

\n\n

Common schema patterns

\n\n

Nullable fields

\n

Use type: [\"string\", \"null\"] (or similar) to allow null values alongside the primary type:

\n\n
nullable.json json 
{\n  \"customer_email\": {\n    \"type\": [\"string\", \"null\"],\n    \"format\": \"email\"\n  }\n}
\n\n

Enums

\n

Restrict a field to a fixed set of values:

\n\n
enum.json json 
{\n  \"status\": {\n    \"type\": \"string\",\n    \"enum\": [\"pending\", \"completed\", \"cancelled\"],\n    \"description\": \"Current order status\"\n  }\n}
\n\n

Nested objects

\n

Describe complex structures with nested properties:

\n\n
nested.json json 
{\n  \"shipping_address\": {\n    \"type\": \"object\",\n    \"required\": [\"street\", \"city\", \"postal_code\"],\n    \"properties\": {\n      \"street\": { \"type\": \"string\" },\n      \"city\": { \"type\": \"string\" },\n      \"postal_code\": { \"type\": \"string\" },\n      \"country\": { \"type\": \"string\", \"default\": \"US\" }\n    }\n  }\n}
\n\n

Schema versioning

\n

As your event sources evolve, you may need to support multiple schema versions. Godzilla allows you to:

\n
    \n
  • Upload a new schema version without removing the old one.
    • \n
  • Specify which schema version a connector uses by default.
    • \n
  • Track which events arrived under which schema for compliance and debugging.
    • \n
\n\n

See the Events concept for how payloads flow through pipelines once validated, and Transforming events in flight for how to reshape them after validation.
