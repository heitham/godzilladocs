Schemas

A schema is a formal declaration of the structure, types, and constraints on an event's payload. Schemas enable validation at ingestion and transformation boundaries, catch malformed data early, and provide explicit contracts between source systems and pipelines.

Why schemas matter

Without a schema, pipelines treat every incoming event as opaque JSON. This works when data is homogeneous and trusted, but quickly becomes fragile:

  • Silent failures: A missing or malformed field goes unnoticed until a transform or destination write fails downstream.
  • Type mismatches: A field that shifts from string to integer silently breaks type-aware transforms.
  • Undocumented contracts: New team members or external systems have no way to know what shape a pipeline expects.

A schema flips the burden: validation happens at the source, errors surface immediately, and the pipeline's data contract is explicit and machine-readable.

Schema formats

Godzilla supports declaring schemas in JSON Schema — the standard dialect for describing JSON structure. A typical schema looks like this:

order_schema.json json 
{\n  \"$schema\": \"http://json-schema.org/draft-07/schema#\",\n  \"type\": \"object\",\n  \"properties\": {\n    \"order_id\": { \"type\": \"string\" },\n    \"amount_cents\": { \"type\": \"integer\", \"minimum\": 0 },\n    \"customer_email\": { \"type\": \"string\", \"format\": \"email\" },\n    \"created_at\": { \"type\": \"string\", \"format\": \"date-time\" }\n  },\n  \"required\": [\"order_id\", \"amount_cents\", \"customer_email\"],\n  \"additionalProperties\": false\n}

This schema declares that an order event must include order_id, amount_cents, and customer_email as required fields; bans any unexpected properties; and enforces type and format constraints.

JSON Schema dialects
Godzilla currently supports JSON Schema draft 7. Other dialects (draft 4, 2019-09, 2020-12) may be supported in future releases.

Registering and attaching schemas

Schemas live in a schema registry — a central repository associated with your Godzilla workspace. You register a schema once, give it a name and version, and then reference it by name in any pipeline.

When a schema is attached to a pipeline's input (the source connector's output) or to a transform step, Godzilla automatically validates each incoming event against that schema. Validation failures are logged and the event is moved to the pipeline's dead-letter queue, not silently dropped.

Validation at transform boundaries

Schemas can also be attached to transform outputs. If a transform is supposed to normalize events to a known shape, attach an output schema to that step:

  • The transform's output is validated against the schema.
  • Validation failures prevent malformed events from reaching the destination.
  • Downstream transforms see a guaranteed contract.

This is especially useful in multi-stage pipelines where one transform's output feeds into another.

Schema versioning
When you update a registered schema, Godzilla treats it as a new version. Pipelines continue using the old version until you explicitly update their schema references. This prevents surprise validation failures from mid-flight schema changes.

Payload validation in practice

When validation is enabled on a pipeline input:

  1. An incoming event arrives from the source connector.
  2. Godzilla validates the event's payload against the attached schema.
  3. If valid, the event proceeds to transforms.
  4. If invalid, the validation error is recorded and the event moves to the dead-letter queue.

The validation report includes the specific constraint that failed (e.g., "missing required field customer_email" or "amount_cents must be ≥ 0"), making debugging straightforward.

Relationship to Events

Every event has a payload; a schema is the optional but recommended way to declare what that payload must look like. Schemas are not required — Godzilla is happy to process unvalidated JSON events — but they catch errors early and make your pipelines more robust.
