Schemas

A schema is a formal declaration of the structure, types, and constraints of an event's payload. Schemas enable validation, type safety, and documentation across your data pipeline.

Why schemas matter

Without a schema, downstream connectors and transforms must guess at the shape of incoming data. With a schema, you get:

  • Validation — Reject or quarantine events that don't match your declared shape, preventing silent data corruption.
  • Type safety — Transforms and destinations know the exact types (string, number, boolean, array, object) of every field.
  • Documentation — The schema serves as a contract between teams, making it clear what data flows through each stage of the pipeline.
  • Evolution — Add or deprecate fields with explicit versioning rules rather than breaking downstream systems unexpectedly.

Schema definition

Godzilla schemas are defined in JSON Schema format (draft 7). A typical schema declares the payload structure:

order.schema.json json 
{\n  "$schema": "http://json-schema.org/draft-07/schema#",\n  "type": "object",\n  "title": "Order Event",\n  "properties": {\n    "order_id": {\n      "type": "string",\n      "pattern": "^ord_[a-zA-Z0-9]+$",\n      "description": "Unique order identifier"\n    },\n    "customer_id": {\n      "type": "string",\n      "description": "Customer who placed the order"\n    },\n    "amount_cents": {\n      "type": "integer",\n      "minimum": 0,\n      "description": "Order total in cents"\n    },\n    "items": {\n      "type": "array",\n      "items": {\n        "type": "object",\n        "properties": {\n          "sku": { "type": "string" },\n          "quantity": { "type": "integer", "minimum": 1 }\n        },\n        "required": ["sku", "quantity"]\n      }\n    }\n  },\n  "required": ["order_id", "customer_id", "amount_cents"]\n}

Declaring a schema

When you create or configure a source connector, you can attach a schema to define the structure of events it produces. Godzilla will validate each incoming event against the schema and reject or route invalid events to the pipeline's dead-letter queue (see Handling errors & retries for details).

Schemas can also be attached to transform steps to ensure that transformed payloads match the expected output contract.

Validation behavior

When an event arrives at a step with an attached schema:

  1. The event's payload is validated against the schema's properties and required constraints.
  2. If validation passes, the event proceeds normally.
  3. If validation fails, the event is tagged with a validation_error and moved to the dead-letter queue (or rejected, depending on pipeline configuration).
Partial schemas

A schema can be partial — it need not define every property in an event's payload. Unknown properties are ignored during validation. This is useful when upstream systems emit extra fields you don't care about.

Schema evolution

As your data needs change, you may need to evolve your schema:

  • Adding optional fields — Add new properties with "required" absent. Existing events will still validate.
  • Making fields required — Carefully add a property to the "required" array. This may break existing events.
  • Changing field types — Consider creating a new event type (e.g., order.created.v2) to avoid breaking transforms that depend on the old type.
  • Deprecating fields — Remove fields from properties and add a deprecation note in your documentation. Validation will continue to ignore them.

Always test schema changes against a sample of real events before deploying to production.

Platform event schemas

Godzilla's own platform events (e.g., pipeline.started, connector.error) have fixed schemas defined by the platform. You cannot modify them, but their schemas are published in the API documentation for use in your webhook handlers and monitoring systems.
