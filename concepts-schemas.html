Schemas

A schema is a declaration of what fields an event payload contains, their types, and which are required. Schemas enable validation at connector boundaries and catch data shape mismatches early.

Why schemas matter

Without schemas, pipelines rely on implicit assumptions about data shape. A source emits a field one day, drops it the next, and your transforms silently fail or produce wrong outputs. Schemas make those assumptions explicit:

  • Validation at source — Reject events that don't match the declared shape before they enter your pipeline.
  • Early error detection — Catch schema drift when a source system changes, not downstream in your destination.
  • Documentation — Your schema is the contract between source and pipeline; SDKs and transforms can auto-document it.
  • Destination compatibility — Guarantee that your destination can ingest the event structure you're sending.

Schema structure

Godzilla schemas follow JSON Schema (draft 7). Here's a simple example:

{{ds:component/code-block|filename=order-events.schema.json|language=json|code={ "$schema": "http://json-schema.org/draft-07/schema#", "title": "Order Event", "type": "object", "required": ["order_id", "amount_cents", "occurred_at"], "properties": { "order_id": { "type": "string", "description": "Unique identifier for the order." }, "amount_cents": { "type": "integer", "description": "Total order amount in cents.", "minimum": 0 }, "occurred_at": { "type": "string", "format": "date-time", "description": "ISO 8601 timestamp." }, "customer_id": { "type": "string", "description": "Optional customer reference." } }, "additionalProperties": false }}}

The schema above declares three required fields (order_id, amount_cents, occurred_at) and one optional field (customer_id). additionalProperties: false means the event payload must not contain any other fields.

Declaring schemas in a pipeline

You attach a schema to a source connector in your pipeline configuration:

{{ds:component/code-block|filename=pipeline.config.json|language=json|code={ "name": "orders-to-warehouse", "version": "1.0", "source": { "type": "postgres", "connection": "prod_orders_db", "table": "orders", "schema": { "$ref": "#/schemas/order-events.schema.json" } }, "destination": { "type": "s3", "bucket": "data-warehouse-prod", "key_prefix": "orders/" } }}}

Alternatively, you can inline the schema directly in the source block, or register it separately via the API and reference it by ID.

Schema Validation Timing

Schemas are validated at the source connector boundary. If an event fails validation, it is rejected and moved to a validation dead-letter queue, not processed by your pipeline. Configure how many consecutive validation failures trigger an alert via the validation_error_threshold pipeline setting.

Schema evolution

As your source systems change, schemas must evolve with them. Adding an optional field is safe — existing events are still valid. Making a field required, removing a field, or changing a field's type is a breaking change:

  • Safe changes — Add an optional field, relax a constraint (e.g. widen a string length limit), or change the order of fields.
  • Breaking changes — Make a field required, remove a field, change a field's type, or tighten a constraint (e.g. reduce a string length limit).

When you make a breaking change, you should create a new pipeline version and update your source connector configuration in lock-step. Old events still conform to the old schema; new events conform to the new one.

Validation and errors

When an event arrives at a source connector that has a schema attached, Godzilla validates it against the schema:

  • Valid event — Passes through to your pipeline transforms and destination.
  • Invalid event — Rejected and sent to the validation dead-letter queue with an error message describing the mismatch (e.g. required field 'order_id' is missing).

You can query validation errors via the Events endpoint by filtering on the status:validation_failed tag.
