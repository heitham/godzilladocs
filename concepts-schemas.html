Schemas

A schema is a declarative definition of the shape, types, and constraints of an event payload. Schemas let you document what data your pipeline expects, validate incoming events, and catch shape mismatches early before they cause silent data loss or corruption downstream.

Why schemas matter

Event payloads are JSON objects that flow from a source connector through transforms to a destination. Without a schema, a malformed event or an unexpected field structure can silently corrupt your pipeline:

  • A missing required field might be silently replaced with null.
  • A field type change (e.g., a string becoming an integer) might be coerced or rejected by a destination, causing events to be dead-lettered.
  • New or removed fields might break downstream systems that expect a fixed shape.

Schemas act as a contract. You declare the expected structure once, and Godzilla validates every event against it. Invalid events are caught immediately and reported rather than propagating errors downstream.

Declaring a schema

Schemas are authored in JSON Schema format (draft 2020-12). A typical schema for user data events looks like this:

order-schema.json json 
{\n  "$schema": "https://json-schema.org/draft/2020-12/schema",\n  "title": "Order Created Event",\n  "type": "object",\n  "properties": {\n    "order_id": { "type": "string", "pattern": "^ord_[0-9a-z]+$" },\n    "customer_id": { "type": "string" },\n    "amount_cents": { "type": "integer", "minimum": 0 },\n    "items": {\n      "type": "array",\n      "items": {\n        "type": "object",\n        "properties": {\n          "sku": { "type": "string" },\n          "qty": { "type": "integer", "minimum": 1 }\n        },\n        "required": ["sku", "qty"]\n      }\n    },\n    "created_at": { "type": "string", "format": "date-time" }\n  },\n  "required": ["order_id", "customer_id", "amount_cents", "created_at"],\n  "additionalProperties": false\n}
\n

This schema defines:

  • Required fields: order_id, customer_id, amount_cents, and created_at must be present on every event.
  • Type constraints: order_id is a string; amount_cents is a non-negative integer.
  • Patterns and formats: order_id must match the regex ^ord_[0-9a-z]+$; created_at must be an RFC 3339 timestamp.
  • Nested shapes: items is an array of objects, each with sku and qty fields.
  • No extra fields: additionalProperties: false means any field not listed is rejected.

Assigning schemas to a pipeline

Once you've defined a schema, you attach it to a pipeline's payload type during pipeline creation or configuration. When you do, Godzilla validates the payload of every event (the payload field in each event object) against that schema.

If an event payload fails validation, the event is rejected with a validation error rather than being silently corrupted. You can inspect validation failures in the pipeline's error logs and metrics, and decide whether to:

  • Fix the schema if your data model evolved and the schema is stale.
  • Fix the source connector or upstream system that produced the invalid event.
  • Relax the schema temporarily if you're tolerating a transition period.

Schema evolution

Schemas are versioned alongside your pipeline versions. When you update a pipeline's schema:

  • New field: Add the field to properties. If you make it required, existing events must be updated before they can flow through. If optional, old events pass validation as-is.
  • Field removal: Remove it from properties. Old events with that field will fail validation unless you allow additionalProperties or explicitly tolerate it.
  • Type change: Changing a field's type is a breaking change — old events will fail the new schema. Use a transform to coerce or normalize values before the validation point if needed.
Schema as documentation

Schemas also serve as machine-readable documentation of your event contract. Tools and dashboards can introspect the schema to show users what fields to expect and which are required.

Validation and error handling

When a validation error occurs, the event is:

  1. Rejected at the validation step.
  2. Logged with details about what failed (missing field, type mismatch, pattern violation, etc.).
  3. Subject to your pipeline's retry and dead-letter settings.

Invalid events do not proceed to transforms or destinations — they stay in the dead-letter queue until you investigate and either repair the source or adjust the schema.
