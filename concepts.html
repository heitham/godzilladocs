Concepts

\n

The three building blocks every Godzilla pipeline is made of.

\n
Start with Pipelines
\n
\n
\n\n
\n

Godzilla is built from three ideas that compose into everything else in these docs. Understanding how they relate makes the rest of the platform — guides, API reference, SDKs — much easier to follow.

\n\n \n Concept\n

Pipelines

\n

Named, versioned workflows that move data from a source to a destination through optional transforms.

\n\n \n Concept\n

Connectors

\n

Pre-built integrations to external systems — sources, destinations, or both.

\n\n \n Concept\n

Events

\n

The atomic unit of data flowing through a pipeline, plus the platform's own lifecycle events.

\n\n \n Concept\n

Schemas

\n

How event payload shapes are declared and validated to ensure data consistency.

\n\n
\n\n
\n

How they fit together

\n

A pipeline reads events from a source connector, transforms them, and writes them to a destination connector. Schemas declare the shape of event payloads, enabling validation and safety checks as data flows through. Everything else in Godzilla — retries, webhooks, monitoring — is built on top of that single loop.

Definitions

\n

Short definitions for terms used throughout these docs.

\n
\n
Pipeline
\n
A named, versioned workflow that moves data from a source connector, through optional transforms, to a destination connector.
\n\n
Connector
\n
A pre-built integration to an external system — a source, a destination, or both.
\n\n
Event
\n
The atomic unit of data moving through a pipeline, or a platform lifecycle notification like pipeline.failed.
\n\n
Webhook
\n
An outbound HTTP request Godzilla sends to a URL you control when a subscribed event occurs.
\n\n
Dead-letter queue
\n
Where an event goes after exhausting its retries, rather than being dropped. See Error handling & recovery.
\n\n
Cursor pagination
\n
The pagination style used by every v2 list endpoint. See Rate limits & errors.
\n\n
Workspace
\n
The top-level account boundary an API key is scoped to.
