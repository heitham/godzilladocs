Fan-out to multiple destinations

In real-world data architectures, you often need to send the same event stream to multiple destination systems — a data warehouse for analytics, a search index for product search, a real-time API for notifications, and so on. This recipe shows how to fan out a single pipeline's output across several destinations.

The pattern

Each Godzilla pipeline has one source and one destination. To fan out to multiple destinations, create one pipeline per destination, all reading from the same source connector:

fanout-pattern.txt text 
Source (Kafka topic)
  ├─ Pipeline A ──> Snowflake (analytics)
  ├─ Pipeline B ──> Elasticsearch (search)
  └─ Pipeline C ──> DynamoDB (real-time API)

All three pipelines read the same events in the same order, but transform and deliver them to their respective destinations independently.

Set up a shared source connector

First, create a single source connector for the data you want to fan out. This example uses a Kafka topic:

create-kafka-source.sh bash 
curl -X POST https://api.godzilladocs.dev/v2/connectors \
  -H "Authorization: Bearer $GODZILLA_API_KEY" \
  -d '{
    "type": "kafka",
    "direction": "source",
    "config": {
      "bootstrap_servers": "kafka.example.com:9092",
      "topic": "user-events",
      "consumer_group": "godzilla-fan-out"
    }
  }'

Store the returned connector_id (e.g., conn_kafka_users) — you'll use it for all downstream pipelines.

Create destination connectors

Next, create one destination connector for each system you're fanning out to:

create-destinations.sh bash 
# Snowflake for analytics
curl -X POST https://api.godzilladocs.dev/v2/connectors \
  -H "Authorization: Bearer $GODZILLA_API_KEY" \
  -d '{
    "type": "snowflake",
    "direction": "destination",
    "config": {"account": "xy12345.us-east-1", "warehouse": "COMPUTE_WH"}
  }'

# Elasticsearch for search
curl -X POST https://api.godzilladocs.dev/v2/connectors \
  -H "Authorization: Bearer $GODZILLA_API_KEY" \
  -d '{
    "type": "elasticsearch",
    "direction": "destination",
    "config": {"hosts": ["elastic.example.com:9200"]}
  }'

# DynamoDB for real-time API
curl -X POST https://api.godzilladocs.dev/v2/connectors \
  -H "Authorization: Bearer $GODZILLA_API_KEY" \
  -d '{
    "type": "dynamodb",
    "direction": "destination",
    "config": {"table_name": "user-events", "region": "us-east-1"}
  }'

Create one pipeline per destination

Now create a pipeline for each destination, all using the same source connector:

create-fanout-pipelines.sh bash 
# Pipeline to Snowflake
curl -X POST https://api.godzilladocs.dev/v2/pipelines \
  -H "Authorization: Bearer $GODZILLA_API_KEY" \
  -d '{
    "name": "user-events-to-snowflake",
    "source_connector_id": "conn_kafka_users",
    "destination_connector_id": "conn_snowflake_analytics"
  }'

# Pipeline to Elasticsearch
curl -X POST https://api.godzilladocs.dev/v2/pipelines \
  -H "Authorization: Bearer $GODZILLA_API_KEY" \
  -d '{
    "name": "user-events-to-elasticsearch",
    "source_connector_id": "conn_kafka_users",
    "destination_connector_id": "conn_elasticsearch_search"
  }'

# Pipeline to DynamoDB
curl -X POST https://api.godzilladocs.dev/v2/pipelines \
  -H "Authorization: Bearer $GODZILLA_API_KEY" \
  -d '{
    "name": "user-events-to-dynamodb",
    "source_connector_id": "conn_kafka_users",
    "destination_connector_id": "conn_dynamodb_api"
  }'

Transform events per destination

Each pipeline can apply different transformations before writing to its destination. For example, reshape data for Elasticsearch's flat schema, or extract only the fields DynamoDB needs:

transformation-example.json json 
{
  "type": "jq",
  "expr": "{ id: .user_id, name: .user_name, email: .user_email, updated_at: now }"
}

Monitor all pipelines

Each pipeline has independent monitoring and alerts. Use the Pipelines endpoint to check the health of each fan-out branch. See Monitoring & alerts for setting up per-pipeline notifications.

Ordering and delivery

All three pipelines will receive events in the same order (because they read from the same Kafka partition group), but they may write to their destinations at slightly different rates depending on network latency and destination throughput. If your use case requires strict ordering across all destinations, use a single pipeline with a custom transformation that writes to all three systems in a transaction, or consider using a message queue pattern instead.
