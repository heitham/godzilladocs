Overview

Fan-out is a common pattern where a single data source feeds multiple destination systems, each potentially with different schemas or transformation logic. This recipe shows how to architect a fan-out pattern in Godzilla to keep data in sync across multiple systems.

Prerequisites

  • A single source connector configured and running
  • Multiple destination connectors ready to receive data
  • Understanding of pipeline transforms (see Building your first pipeline)

Approach 1: Multiple pipelines from one source

How it works

Create a separate pipeline for each destination, all reading from the same source. Each pipeline can have its own transform logic, error handling, and monitoring.

Advantages

  • Complete independence between destinations—a failure in one pipeline doesn't affect others
  • Different SLAs and retry policies per destination
  • Easier to debug and troubleshoot individual data flows

Disadvantages

  • Higher infrastructure cost (more pipelines to run and monitor)
  • Duplicate transform logic if destinations share the same schema

Approach 2: Single pipeline with multiple destinations

How it works

Create one pipeline that reads from the source and writes to multiple destinations. Use conditional routing in your transforms to send different subsets of data to different destinations if needed.

{{ds:component/code-block|filename=pipeline-config.json|language=json|code={\n "source": "crm-system",\n "destinations": [\n {\n "name": "data-warehouse",\n "filter": "event.type == 'customer.updated'"\n },\n {\n "name": "analytics-platform",\n "filter": "true"\n },\n {\n "name": "email-service",\n "filter": "event.type == 'customer.created'"\n }\n ]\n}}}

Advantages

  • Lower operational overhead—one pipeline to monitor and maintain
  • Single transform step applied to all destinations
  • Easier to ensure all destinations see the same data

Disadvantages

  • A failure in any destination can block the entire pipeline
  • Less flexibility if destinations need very different data models
  • Harder to apply destination-specific retries or error handling

Recommended pattern

For most use cases, we recommend multiple pipelines with shared transforms:

  1. Use a dedicated transform library or stored procedures to avoid duplicating business logic
  2. Create one pipeline per destination, but reference the same transform function in each
  3. Monitor each pipeline independently while sharing the transform definition
  4. Set destination-specific error handling and retry policies as needed

This balances the independence and debuggability of multiple pipelines with the code-reuse benefits of a single transform layer.

Monitoring fan-out patterns

When using multiple pipelines, set up alerting to catch skew between destinations:

  • Compare event counts across pipelines at regular intervals
  • Alert if one pipeline's lag exceeds a threshold (e.g., more than 5 minutes behind)
  • Monitor dead-letter queues in each pipeline independently
  • Use webhooks to track successful deliveries to each destination

See Monitoring & alerts for setup details.
