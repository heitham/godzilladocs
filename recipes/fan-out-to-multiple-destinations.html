Fan-out to multiple destinations

In modern data architectures, a single event stream often serves multiple consumers—such as sending purchase events to Snowflake for analytics, Elasticsearch for real-time indexing, and an external webhook for partner notifications. This recipe demonstrates how to implement the fan-out pattern in Godzilla with complete fault isolation between destinations.

Why fan out with independent pipelines?

While you could theoretically push data through a monolithic multi-target job, Godzilla recommends creating separate pipelines attached to a single shared source connector. This pattern provides essential architectural guarantees:

  • Fault isolation: An outage or slow write in one destination does not delay or block deliveries to other destinations.
  • Independent retries and DLQs: Failed deliveries to a partner webhook retry independently without impacting your data warehouse sync.
  • Tailored transformations: Each pipeline applies transforms specific to its destination schema (e.g. masking PII for search while storing full records in cold storage).

1. Create a shared source connector

First, create the primary source connector that reads events once from your upstream system (such as Postgres CDC or Kafka).

create-source.sh bash 
curl -X POST https://api.godzilladocs.dev/v2/connectors \
  -H "Authorization: Bearer $GODZILLA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "orders-source-postgres",
    "type": "postgres",
    "direction": "source",
    "config": {
      "connection_string": "postgres://user:secret@db.internal:5432/production",
      "tables": ["public.orders"]
    }
  }'

2. Create destination connectors

Next, set up the individual destination connectors for each target system.

create-destinations.sh bash 
# Destination 1: Snowflake Data Warehouse
curl -X POST https://api.godzilladocs.dev/v2/connectors \
  -H "Authorization: Bearer $GODZILLA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name":"analytics-snowflake","type":"snowflake","direction":"destination","config":{"account":"xy12345","database":"analytics"}}'

# Destination 2: Webhook for notifications
curl -X POST https://api.godzilladocs.dev/v2/connectors \
  -H "Authorization: Bearer $GODZILLA_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name":"partner-webhook","type":"webhook","direction":"destination","config":{"url":"https://partner.example.com/events"}}'

3. Wire up dedicated pipelines with specialized transforms

Create a pipeline for each destination referencing the shared source_connector_id. Configure custom transforms per pipeline.

fanout-pipelines.json json 
# Pipeline 1: Analytics (Full schema enrichment)
{
  "name": "fanout-to-snowflake",
  "source_connector_id": "conn_pg_orders",
  "destination_connector_id": "conn_snowflake_dw",
  "transforms": [
    {"type": "enrich", "fields": {"synced_at": "$now"}}
  ]
}

# Pipeline 2: Webhook (Filtered & stripped PII)
{
  "name": "fanout-to-webhook",
  "source_connector_id": "conn_pg_orders",
  "destination_connector_id": "conn_partner_hook",
  "transforms": [
    {"type": "filter", "condition": "payload.total_cents > 10000"},
    {"type": "reshape", "mapping": {"order_id": "payload.id", "status": "payload.status"}}
  ]
}
Independent retry policies

Because the pipelines are independent, you can assign an aggressive retry policy to your data warehouse pipeline while setting a lenient retry policy with a longer timeout for third-party webhooks.

4. Monitoring fan-out streams

Each pipeline exposes its own throughput, latency, and error metrics. Use Monitoring & alerts to subscribe to webhook alerts for pipeline.failed across all pipelines in your workspace.
