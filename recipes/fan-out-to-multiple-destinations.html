Fan-out to multiple destinations

A common architecture pattern is to stream events from a single source system to multiple destinations. This recipe shows how to set up parallel pipelines so events reach warehouses, real-time analytics platforms, and operational databases simultaneously.

Overview

Fan-out workflows let you:

  • Maintain a single source of truth while serving multiple downstream systems
  • Process the same events through different transforms for each destination
  • Decouple destination failures from affecting other pipelines

Creating multiple pipelines

Create a separate pipeline for each destination, all reading from the same source connector:

create-pipelines.sh bash 
# Pipeline 1: to data warehouse
curl -X POST https://api.godzilladocs.dev/v2/pipelines \\
  -H "Authorization: Bearer $GODZILLA_API_KEY" \\
  -d '{
    "name": "events-to-warehouse",
    "source_connector_id": "conn_kafka_events",
    "destination_connector_id": "conn_snowflake_warehouse"
  }'

# Pipeline 2: to real-time analytics
curl -X POST https://api.godzilladocs.dev/v2/pipelines \\
  -H "Authorization: Bearer $GODZILLA_API_KEY" \\
  -d '{
    "name": "events-to-analytics",
    "source_connector_id": "conn_kafka_events",
    "destination_connector_id": "conn_mixpanel_analytics"
  }'

# Pipeline 3: to operational database
curl -X POST https://api.godzilladocs.dev/v2/pipelines \\
  -H "Authorization: Bearer $GODZILLA_API_KEY" \\
  -d '{
    "name": "events-to-operational-db",
    "source_connector_id": "conn_kafka_events",
    "destination_connector_id": "conn_postgres_operational"
  }'

Transforming for each destination

Each pipeline can apply destination-specific transforms without affecting others. For example, reshape the event schema for your warehouse while filtering sensitive fields for analytics:

transform-for-warehouse.json json 
{
  "transform_type": "jq",
  "script": ". | {event_id, user_id, timestamp, event_type, properties: .properties | del(.internal_notes, .cost)}"
}

Error handling

Each pipeline has independent error and retry policies. If one destination fails:

Isolated failures

Events retry only in the failed pipeline; other pipelines continue delivering to their destinations. Use the Events API to monitor each pipeline's delivery status independently.

Monitoring fan-out pipelines

Check delivery status across all destination pipelines:

monitor-pipelines.sh bash 
for pipeline in "events-to-warehouse" "events-to-analytics" "events-to-operational-db"; do
  echo "=== $pipeline ==="
  curl https://api.godzilladocs.dev/v2/events \\
    -H "Authorization: Bearer $GODZILLA_API_KEY" \\
    -d "{\"pipeline_id\": \"$pipeline\", \"status\": \"delivered\"}"
done
