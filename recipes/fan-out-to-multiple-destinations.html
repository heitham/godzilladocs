Fan-out to multiple destinations

\n

A common architecture pattern is to stream events from a single source system to multiple destinations. This recipe shows how to set up parallel pipelines so events reach warehouses, real-time analytics platforms, and operational databases simultaneously.

\n\n

Overview

\n

Fan-out workflows let you:

\n
    \n
  • Maintain a single source of truth while serving multiple downstream systems
    • \n
  • Process the same events through different transforms for each destination
    • \n
  • Decouple destination failures from affecting other pipelines
    • \n
\n\n

Creating multiple pipelines

\n

Create a separate pipeline for each destination, all reading from the same source connector:

\n\n
\n
\n create-pipelines.sh\n bash\n \n
\n 
# Pipeline 1: to data warehouse\ncurl -X POST https://api.godzilladocs.dev/v2/pipelines \\\n  -H \"Authorization: Bearer $GODZILLA_API_KEY\" \\\n  -d '{\n    \"name\": \"events-to-warehouse\",\n    \"source_connector_id\": \"conn_kafka_events\",\n    \"destination_connector_id\": \"conn_snowflake_warehouse\"\n  }'\n\n# Pipeline 2: to real-time analytics\ncurl -X POST https://api.godzilladocs.dev/v2/pipelines \\\n  -H \"Authorization: Bearer $GODZILLA_API_KEY\" \\\n  -d '{\n    \"name\": \"events-to-analytics\",\n    \"source_connector_id\": \"conn_kafka_events\",\n    \"destination_connector_id\": \"conn_mixpanel_analytics\"\n  }'\n\n# Pipeline 3: to operational database\ncurl -X POST https://api.godzilladocs.dev/v2/pipelines \\\n  -H \"Authorization: Bearer $GODZILLA_API_KEY\" \\\n  -d '{\n    \"name\": \"events-to-operational-db\",\n    \"source_connector_id\": \"conn_kafka_events\",\n    \"destination_connector_id\": \"conn_postgres_operational\"\n  }'
\n
\n\n

Transforming for each destination

\n

Each pipeline can apply destination-specific transforms without affecting others. For example, reshape the event schema for your warehouse while filtering sensitive fields for analytics:

\n\n
\n
\n transform-for-warehouse.json\n json\n \n
\n 
{\n  \"transform_type\": \"jq\",\n  \"script\": \". | {event_id, user_id, timestamp, event_type, properties: .properties | del(.internal_notes, .cost)}\"\n}
\n
\n\n

Error handling

\n

Each pipeline has independent error and retry policies. If one destination fails:

\n\n
\n
Isolated failures
\n

Events retry only in the failed pipeline; other pipelines continue delivering to their destinations. Use the Events API to monitor each pipeline's delivery status independently.

\n
\n\n

Monitoring fan-out pipelines

\n

Check delivery status across all destination pipelines:

\n\n
\n
\n monitor-pipelines.sh\n bash\n \n
\n 
for pipeline in \"events-to-warehouse\" \"events-to-analytics\" \"events-to-operational-db\"; do\n  echo \"=== $pipeline ===\"\n  curl https://api.godzilladocs.dev/v2/events \\\n    -H \"Authorization: Bearer $GODZILLA_API_KEY\" \\\n    -d \"{\\\"pipeline_id\\\": \\\"$pipeline\\\", \\\"status\\\": \\\"delivered\\\"}\"\ndone
