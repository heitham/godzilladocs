Backfill historical data

When connecting a new destination or onboarding a new dataset, you often need to ingest historical records in addition to streaming new changes. This recipe demonstrates how to run large-scale historical backfills through a pipeline safely without exhausting rate limits or blocking live events.

Prerequisites

Ensure your source and destination connectors are active and verified. See Connecting a data source for setup details.

Architecture overview

Rather than modifying your live streaming pipeline, create a dedicated backfill pipeline with bounded source offsets. This provides two key benefits:

  • Workload isolation: High-throughput backfill traffic does not starve or add latency to real-time events.
  • Custom rate limits: You can tune concurrency, batch sizes, and retry backoffs specifically for bulk loading.

1. Create a dedicated backfill pipeline

Use the Pipelines endpoint to create a pipeline configured with bounded timestamps or query constraints on the source connector.

create-backfill-pipeline.sh bash 
{
  "name": "backfill-orders-2025",
  "source_connector_id": "conn_pg_orders",
  "destination_connector_id": "conn_snowflake_dw",
  "config": {
    "mode": "backfill",
    "start_timestamp": "2025-01-01T00:00:00Z",
    "end_timestamp": "2025-12-31T23:59:59Z",
    "batch_size": 5000,
    "max_concurrency": 4
  }
}

2. Configure transform rules for bulk ingestion

Bulk backfills may contain legacy data formats or outdated schema versions. Attach schema normalization transforms to map older records into your current target format.

backfill-transforms.json json 
{
  "transforms": [
    {
      "type": "enrich",
      "fields": {
        "is_backfill": true,
        "backfilled_at": "$now"
      }
    },
    {
      "type": "reshape",
      "mapping": {
        "id": "payload.order_id",
        "amount": "payload.total_price",
        "created_at": "payload.created_at"
      }
    }
  ]
}

3. Managing destination rate limits and quotas

Backfills push high volumes of data in short periods. Avoid throttling destination systems by adjusting concurrency settings and observing platform quotas.

Throttle to protect downstream systems

If your destination database or API enforces strict write quotas, set max_concurrency low and monitor Rate limits to prevent cascading 429 status codes.

4. Monitoring and verifying completion

Track progress by checking pipeline metrics or subscribing to platform lifecycle events. When all historical records have been processed, the backfill pipeline status transitions to completed.

check-status.sh bash 
curl https://api.godzilladocs.dev/v2/pipelines/pipe_backfill_2025/stats \
  -H "Authorization: Bearer $GODZILLA_API_KEY"

If any individual records fail, inspect the dead-letter queue and replay failed records as described in Error handling & recovery.
