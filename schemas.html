Schemas

A schema defines the shape and types of an event's payload. It describes what fields must or may be present, what data types they should have, and any constraints or validation rules.

Why schemas matter

Schemas serve several critical purposes in a Godzilla pipeline:

  • Validation — Catch malformed events early. If an event doesn't match its schema, the pipeline can reject it or route it to the dead-letter queue.
  • Documentation — Make it explicit what your pipeline expects. Team members and integrating systems know exactly what fields a pipeline ingests.
  • Transformation safety — Transform steps can trust that fields they reference actually exist and have the right type.
  • Monitoring — Track schema drift. If a source system starts emitting unexpected shapes, your monitoring will flag it.

Schema format

Godzilla uses JSON Schema (draft 2020-12) to declare event payload shapes. A schema specifies the type of the payload object, required fields, and type constraints for each property:

{{ds:component/code-block|filename=order-schema.json|language=json|code={%0A "$schema": "https://json-schema.org/draft/2020-12/schema",%0A "type": "object",%0A "properties": {%0A "order_id": { "type": "string" },%0A "customer_id": { "type": "string" },%0A "amount_cents": { "type": "integer", "minimum": 0 },%0A "currency": { "type": "string", "enum": ["USD", "EUR", "GBP"] },%0A "metadata": { "type": "object" }%0A },%0A "required": ["order_id", "customer_id", "amount_cents"]%0A}}}

Associating a schema with a pipeline

You attach a schema to a connector or pipeline step when you want strict validation. During pipeline execution, every event processed through that step is checked against the schema. Events that fail validation are handled according to your pipeline's error policy — typically retried, then dead-lettered.

Optional schemas

Schemas are optional. You may have a pipeline that accepts any payload and relies on downstream transforms to handle variation. However, declaring a schema is a best practice for data quality and observability.

Common schema patterns

Strict object with required fields

Ensures the payload must be an object with a specific set of fields. Unknown properties are rejected:

{{ds:component/code-block|filename=strict-schema.json|language=json|code={%0A "type": "object",%0A "properties": {%0A "id": { "type": "string", "format": "uuid" },%0A "status": { "type": "string" }%0A },%0A "required": ["id", "status"],%0A "additionalProperties": false%0A}}}

Flexible object with optional fields

Allows extra fields beyond the schema. Useful when the source system may add new fields over time:

{{ds:component/code-block|filename=flexible-schema.json|language=json|code={%0A "type": "object",%0A "properties": {%0A "id": { "type": "string" },%0A "timestamp": { "type": "string", "format": "date-time" }%0A },%0A "required": ["id"],%0A "additionalProperties": true%0A}}}

Nested objects

Payloads often contain nested structures. Define schemas for sub-objects using the same properties pattern:

{{ds:component/code-block|filename=nested-schema.json|language=json|code={%0A "type": "object",%0A "properties": {%0A "user_id": { "type": "string" },%0A "address": {%0A "type": "object",%0A "properties": {%0A "street": { "type": "string" },%0A "city": { "type": "string" },%0A "postal_code": { "type": "string" }%0A },%0A "required": ["city", "postal_code"]%0A }%0A },%0A "required": ["user_id", "address"]%0A}}}

Validation at different stages

You can attach schemas at multiple points in a pipeline:

  • Source connector — Validates events as they enter the pipeline from your source system. Rejects malformed records immediately.
  • Transform step — Validates the shape of data after a transform. Ensures your transform logic produces the correct shape.
  • Destination connector — Validates before writing to the destination. Some destinations (databases, APIs) require specific shapes.

Handling schema mismatches

When an event fails schema validation, your pipeline's error policy determines what happens:

  • Retry with backoff — If the failure might be transient (source system is momentarily inconsistent), retry the event.
  • Dead-letter — Send the event to the pipeline's dead-letter queue for manual inspection and recovery.
  • Skip — Some pipelines drop invalid events silently (use with caution — you lose observability).

See Handling errors & retries for detailed configuration.

Evolving schemas

Real systems change over time. When you need to evolve a schema:

  • Add an optional field — Simply add the property without including it in required. Old events without that field still pass.
  • Remove a field — Delete the property from properties. Events with that field still pass (backward compatible) unless you set additionalProperties: false.
  • Change a type — Use union types or oneOf to accept multiple types during a transition period, then lock it down once all data has migrated.
Breaking changes

Some schema changes are breaking. If you make a required field optional, or remove constraints, old events pass. If you add a required field or make constraints stricter, some events will start failing validation.
