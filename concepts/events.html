Events

\n

An event is the atomic unit of data that moves through a Pipeline. Every record a source connector emits, every row a transform produces, and every write a destination connector performs is an event.

\n\n

Event shape

\n
\n
\n event.json\n json\n \n
\n 
{\n  "id": "evt_8f2c1a90",\n  "type": "order.created",\n  "occurred_at": "2026-08-18T09:12:44Z",\n  "source": "connector_postgres_orders",\n  "payload": { "order_id": "ord_4471", "amount_cents": 4899 }\n}

\n\n

User data events vs. platform events

\n

Godzilla distinguishes two kinds of events:

\n
    \n
  • User data events — the records your pipelines process, shaped however your source system produces them.
    • \n
  • Platform events — lifecycle notifications Godzilla itself emits: pipeline.started, pipeline.completed, pipeline.failed, connector.error. These are what power Webhooks.
    • \n
\n\n
\n
Ordering
\n

Events are delivered in-order per source partition, not globally. Two events from different source partitions may be processed out of order relative to each other.

\n
\n\n

Payload shape and validation

\n

Every event carries a payload — the actual user data. To ensure payload consistency and enable validation, you declare the expected shape of a payload using a schema. Schemas let connectors validate incoming data and allow transform code to safely access fields with IDE autocomplete.

\n

Learn how to declare and use schemas in the Schemas concept guide.

\n\n

Retries and dead-lettering

\n

An event that fails a transform or destination write is retried with exponential backoff. After the configured retry limit, it is moved to that pipeline's dead-letter queue rather than dropped. See Error handling & recovery for how to configure and drain a dead-letter queue.
