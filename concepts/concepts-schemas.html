Schemas

A schema is a declarative contract that defines the expected structure, data types, and required fields for an event payload moving through a pipeline. Schemas prevent malformed records from propagating downstream and ensure data integrity across source and destination connectors.

Declaring a schema

Godzilla schemas follow standard JSON Schema (Draft-07) specifications. You define schemas per event type or attach them directly to pipeline ingress and egress stages.

{{ds:component/code-block|filename=order-created.schema.json|language=json|code={ "$schema": "http://json-schema.org/draft-07/schema#", "title": "OrderCreatedPayload", "type": "object", "properties": { "order_id": { "type": "string" }, "customer_id": { "type": "string" }, "amount_cents": { "type": "integer", "minimum": 0 }, "currency": { "type": "string", "enum": ["USD", "EUR", "GBP"] }, "status": { "type": "string" } }, "required": ["order_id", "amount_cents", "currency"], "additionalProperties": false }}}

Validation & enforcement modes

When a pipeline processes an event, Godzilla validates the payload against the registered schema. You can configure how validation failures are handled using one of three enforcement modes:

  • strict — Any event failing validation is immediately rejected and routed to the pipeline's dead-letter queue.
  • warn — The event continues through the pipeline, but a platform warning event is emitted for monitoring and alerting.
  • drop — Invalid events are silently discarded without halting pipeline execution or triggering retries.
Validation failure handling

In strict mode, validation errors do not retry endlessly. Because payload schema mismatches are deterministic, failed events bypass transient retries and move straight to the dead-letter queue. See Error handling & recovery for details on inspecting and replaying dead-lettered events.

Schema validation in the pipeline lifecycle

Validation can occur at three points in a pipeline run:

  1. Ingress validation — Verified immediately after a source connector emits an event, ensuring source data conforms to expectations.
  2. Post-transform validation — Verified after transform steps run to confirm reshaped payloads match target specifications.
  3. Egress validation — Checked before writing to a destination connector to guarantee downstream compatibility.

Schema evolution & compatibility

As business requirements change, schemas evolve. Godzilla supports backward and forward compatibility rules to prevent breaking active pipelines:

  • Additive changes — Adding optional fields is backward-compatible and does not require pipeline downtime.
  • Breaking changes — Removing fields or adding new required fields requires creating a new pipeline version or using a transform step to migrate payload shapes.
