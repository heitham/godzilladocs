Schemas

A schema is a formal declaration of the structure and types within an event payload. It defines what fields are present, their types, and validation rules so that your pipeline can enforce data quality at every step.

Why schemas matter

Without schemas, it is easy for downstream systems to receive unexpected field shapes, missing values, or type mismatches. Schemas give you:

  • Validation — reject or repair events that do not conform before they reach destination connectors.
  • Documentation — auto-generated schema definitions become your contract with downstream teams.
  • Evolution tracking — version your schemas and migrate data as structures change over time.
  • Tooling support — IDEs and code generators use schemas to offer autocomplete and type safety.

Schema formats

Godzilla supports multiple schema declaration standards:

  • JSON Schema (default) — widely used, human-readable, and natively supported across most tools.
  • Apache Avro — binary-safe, strongly typed, and optimized for high-throughput serialization.
  • Protocol Buffers — compact binary format with versioning built in, ideal for microservice contracts.
order.schema.json json 
{\\n  "$schema": "http://json-schema.org/draft/2020-12",\\n  "type": "object",\\n  "title": "Order Event",\\n  "required": ["order_id", "customer_id", "amount_cents"],\\n  "properties": {\\n    "order_id": { "type": "string", "pattern": "^ord_[0-9a-z]+$" },\\n    "customer_id": { "type": "string" },\\n    "amount_cents": { "type": "integer", "minimum": 0 },\\n    "notes": { "type": "string", "maxLength": 500 }\\n  },\\n  "additionalProperties": false\\n}

Validation modes

When an event arrives at a transform or destination connector, the schema validator can:

  • Strict — reject any event that does not fully conform; the event goes to dead-letter.
  • Coerce — attempt to convert types (e.g., string 123 to integer 123) and fill in optional fields with defaults.
  • Pass-through — log warnings but allow non-conforming events to proceed; useful during migration phases.
Schema Mismatch

If you change a schema while events with the old structure are still being processed, use coerce mode temporarily to avoid dead-lettering a large backlog of valid but structurally older events.

Registering and versioning schemas

Schemas live in a central registry so that all connectors can reference them by name and version. When you deploy a new schema version, existing pipelines continue using the previous version until you explicitly promote them.

This staged approach prevents surprise incompatibilities and gives you time to test new shapes in non-production pipelines first.

How events and schemas work together

Every event flowing through a pipeline is validated against the schema registered for its type. If the event has a type field like order.created, the validator looks up the schema for order.created, checks it against the payload, and either passes or rejects the event based on your validation mode.
