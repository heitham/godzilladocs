Schemas

A schema defines the structural contract for an event's payload. While Godzilla enforces a standard top-level event envelope, schemas declare the exact data types, required properties, and value constraints of the user payload inside each event.

Declaring event payload shapes

Schemas in Godzilla use standard JSON Schema (draft-07) specifications. Each schema maps to an event type and declares what fields must be present and what data formats they must follow.

order-created.schema.json json 
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "OrderCreatedPayload",
  "type": "object",
  "required": ["order_id", "customer_id", "amount_cents", "currency"],
  "properties": {
    "order_id": {
      "type": "string",
      "pattern": "^ord_[a-zA-Z0-9]+$"
    },
    "customer_id": {
      "type": "string"
    },
    "amount_cents": {
      "type": "integer",
      "minimum": 0
    },
    "currency": {
      "type": "string",
      "enum": ["USD", "EUR", "GBP", "CAD"]
    },
    "metadata": {
      "type": "object"
    }
  },
  "additionalProperties": false
}

Payload validation lifecycle

Validation runs automatically as data moves through a pipeline:

  1. Source ingestion: When a source connector emits an event, Godzilla matches the event's type against the registered schema and validates the payload.
  2. Transform boundaries: After each transform step that alters payload structures, the output can be re-validated before continuing down the pipeline.
  3. Destination write: Ensures only schema-compliant events reach destination sinks (such as Snowflake or PostgreSQL).
Validation occurs at runtime

Schema enforcement happens at event ingestion before expensive transforms or downstream writes occur. Malformed payloads are trapped early, protecting downstream systems from invalid state.

Validation modes

Pipelines can configure one of three validation modes depending on your data guarantees:

Mode Behavior on valid payload Behavior on invalid payload
strict Processed through pipeline Rejected immediately; event is moved to the dead-letter queue
permissive Processed through pipeline Processed with a validation_warning attribute attached and metric incremented
disabled Processed through pipeline Bypasses payload validation checks completely

Handling validation failures

When an event fails validation under strict mode, Godzilla emits a validation.failed error, cancels downstream processing for that event, and routes it to the pipeline's dead-letter queue. The dead-lettered record includes detailed validation diagnostics:

  • failing_path — the JSON pointer to the invalid field (e.g. /payload/amount_cents).
  • constraint — the rule that failed (e.g. minimum or required).
  • received_value — the actual invalid value received.

To inspect and replay failed events after correcting schema definitions or source data, see the Error handling & recovery guide and the Events replay endpoint.

Schema versioning and evolution

Event schemas evolve as your application grows. Godzilla supports backwards-compatible schema changes without downtime:

  • Additive changes: Adding optional fields or expanding enum values are non-breaking and can be deployed without updating existing event consumers.
  • Breaking changes: Adding required fields, removing fields, or changing data types require publishing a new schema version (e.g. order.created.v2) or applying a transform. See Transforming events in flight for reshaping payloads during migrations.
