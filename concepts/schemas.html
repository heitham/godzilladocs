Schemas

A schema defines the expected shape and structure of an event's payload. Schemas allow you to declare what fields an event should contain, what types they should be, and which fields are required. Godzilla validates incoming events against their schema and can route invalid events to your pipeline's dead-letter queue.

Schema definition

Schemas are declared as JSON Schema documents. Each schema specifies the properties expected in an event's payload field, plus validation constraints.

order-event-schema.json json 
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "Order Event",
  "type": "object",
  "properties": {
    "order_id": { "type": "string" },
    "customer_id": { "type": "string" },
    "amount_cents": { "type": "integer", "minimum": 0 },
    "currency": { "type": "string", "default": "USD" },
    "items": {
      "type": "array",
      "items": { "type": "object" }
    }
  },
  "required": ["order_id", "customer_id", "amount_cents"]
}

Validation and error handling

When a pipeline receives an event, Godzilla validates it against the assigned schema before processing. If validation fails:

  • The event is marked as failed.
  • A validation error detail is recorded.
  • The event is routed through the standard retry loop with exponential backoff.
  • After the retry limit is exhausted, the event is moved to the pipeline's dead-letter queue.
Schema validation timing

Validation occurs as soon as an event is ingested, before any transforms are applied. This ensures that all downstream processing operates on data that matches expectations.

Assigning schemas to event types

Schemas are assigned to event types at the pipeline level. An event type like order.created can be validated against a specific schema version, and you can update the schema independently when your data model evolves.

pipeline-config.json json 
{
  "pipeline": "order-ingestion",
  "source": "connector_kafka_orders",
  "schemas": {
    "order.created": {
      "version": "1.0",
      "definition": ... 
    },
    "order.updated": {
      "version": "1.0",
      "definition": ...
    }
  }
}

Versioning and evolution

Schemas support semantic versioning, allowing you to evolve your event structure safely:

  • Patch updates (1.0.1) — Fix validation rules without changing the structure.
  • Minor updates (1.1.0) — Add optional fields or loosen constraints.
  • Major updates (2.0.0) — Change required fields or restructure the payload.

When you update a schema, existing pipelines continue using their pinned version until you explicitly roll forward, giving you time to test and migrate downstream systems.

Schema defaults

If no schema is assigned to an event type, Godzilla does not validate the payload — all events pass through without structural checks. You can add schemas incrementally as your pipelines mature.

Dead-letter queue inspection

Invalid events appear in your pipeline's dead-letter queue with detailed error metadata, letting you audit failures and reprocess events once the underlying issue is fixed. See Handling errors & retries for how to drain and replay dead-lettered events.
