Schemas

\n

A schema is a declaration of the shape and types of fields in an event payload. Schemas ensure data consistency as events flow through your pipelines, allow destinations to validate incoming data, and power IDE autocomplete and validation in transforms.

\n\n

Why schemas matter

\n

Without explicit schemas, a pipeline has no way to know whether an incoming event's payload matches what the destination expects. Schemas solve this by:

\n
    \n
  • Validating — Rejecting events that don't match the declared shape before they reach a destination.
    • \n
  • Documenting — Making it clear to other engineers what fields a pipeline carries and what types they have.
    • \n
  • Enabling safety checks — Detecting schema drift (unplanned changes to event shape) as data sources evolve.
    • \n
  • Powering transforms — In transform code, your IDE can autocomplete fields because it knows the schema.
    • \n
\n\n

Declaring a schema

\n

Schemas are declared at the connector level, not at the pipeline level. A source connector declares the shape of events it emits; a destination connector declares the shape it expects to receive.

\n\n
\n
\n connector-schema.json\n json\n \n
\n 
{\n  \"fields\": [\n    {\n      \"name\": \"order_id\",\n      \"type\": \"string\",\n      \"required\": true,\n      \"description\": \"Unique order identifier\"\n    },\n    {\n      \"name\": \"amount_cents\",\n      \"type\": \"integer\",\n      \"required\": true,\n      \"description\": \"Order total in cents\"\n    },\n    {\n      \"name\": \"customer_id\",\n      \"type\": \"string\",\n      \"required\": false\n    },\n    {\n      \"name\": \"tags\",\n      \"type\": \"array\",\n      \"items\": { \"type\": \"string\" },\n      \"required\": false\n    }\n  ]\n}
\n
\n\n

Each field declares:

\n
    \n
  • name — The field key as it appears in the event payload.
    • \n
  • type — One of string, integer, number, boolean, object, array, or null.
    • \n
  • required — Whether the field must be present in every event.
    • \n
  • description (optional) — Human-readable explanation of what the field contains.
    • \n
\n\n

Validation during processing

\n

When an event flows through a pipeline, Godzilla validates the payload against the source connector's declared schema. If validation fails:

\n
    \n
  • The event is marked with a validation error.
    • \n
  • It is not passed to transforms or the destination.
    • \n
  • It is moved to the pipeline's dead-letter queue.
    • \n
\n\n

This prevents corrupted or malformed data from corrupting downstream systems. See Error handling & recovery to learn how to inspect and replay dead-lettered events.

\n\n

Schema evolution

\n

As your source systems evolve, you may need to add or change fields in a schema. Godzilla supports schema evolution through versioning:

\n\n
\n
Backward compatibility
\n

When adding a new field to a source schema, make it optional (required: false) to avoid breaking existing pipelines. When removing a field, plan a deprecation period and alert connected destinations.

\n
\n\n

Connecting the dots

\n

Schemas sit between Events and Connectors:

\n
    \n
  • Events carry the actual data; schemas declare what shape that data should have.
    • \n
  • Connectors (both source and destination) each have their own schema, defining what they emit and what they expect.
    • \n
  • A transform can reshape event payloads before they reach a destination, allowing you to map between different connector schemas.
    • \n
